# Marketplace image — retained-access audit

**Audited:** 2026-07-26.
**Scope:** the four written claims below, against the **Azure** image build
pipeline first and then the **AWS** one, for both products.
**Repos read:** `hailbytes-sat` @ `9237c95`, `hailbytes-asm` @ `495d847`,
`hailbytes-terraform-modules` @ `ad4b352`.

**The claims as made to the customer:**

1. No HailBytes SSH key baked into the marketplace images.
2. No reverse-tunnel agent.
3. No phone-home daemon.
4. No license-server heartbeat.
5. The product functions with all egress closed except customer-chosen
   integrations.

**Verdict: claims 1, 2 and 4 hold. Claim 5 holds with three named
exceptions, none of them HailBytes-controlled. Claim 3 holds as written but
you should re-state it — the images ship default-on browser error reporting to
a HailBytes-owned Sentry project in the United States, and a security reviewer
will call that a phone-home even though it is not a daemon and does not run on
the VM.**

The Azure and AWS images are built from **one** Packer template with one shared
provisioner and one shared sanitiser, so every finding below applies identically
to both clouds unless stated otherwise. That is a real strength of the pipeline:
there is no separate Azure code path that could drift.

## Claim 1 — No HailBytes SSH key baked in

**✅ CONFIRMED, both clouds.**

| Evidence | Where |
|---|---|
| No SSH public key literal exists anywhere in either product repo. A repo-wide search for `(ssh-rsa\|ssh-ed25519\|ecdsa-sha2-nistp256) AAAA…` matches only Terraform **test fixtures** in `modules/*/azure/tests/*.tftest.hcl` — mock-provider inputs, never applied. | `hailbytes-sat`, `hailbytes-asm` |
| No code appends to `authorized_keys`. A search for `>> …authorized_keys` / `tee …authorized_keys` returns nothing in either repo. | both |
| The sanitiser **shreds** every SSH artifact before capture: `authorized_keys` (and `.old`/`~`/`.*` variants), `known_hosts`, `~/.ssh/config`, and any `id_*` / `*.pub` / `*.pem`, for `ubuntu` and `root`, followed by a catch-all `find "$ssh_dir" -type f -exec secure_remove {}`. Host keys are removed (`rm -f /etc/ssh/ssh_host_*`) and regenerated by cloud-init on first boot. | `hailbytes-sat/scripts/sanitize_vm.sh` |
| A final verification loop re-checks each sensitive path and prints `WARNING: <file> still exists!` if any survived. | same |
| The build VM's own credential is ephemeral. Azure: Packer's `ssh_username = "packer"`, and the build runs `/usr/sbin/waagent -force -deprovision+user`, which deletes the build user and its `.ssh`. AWS: `ssh_username = "ubuntu"`, and that user's keys are shredded by the sanitiser. | `scripts/packer/hailbytes-sat.pkr.hcl`, `scripts/sanitize_vm.sh` |
| Hardening disables root login and password auth: `PermitRootLogin no`, `PasswordAuthentication no` (unless the operator sets `ALLOW_SSH_PASSWORD`), and root's shadow entry is blanked to `*`. | `scripts/hailbytes-sat-harden-ubuntu-2404.sh`, `scripts/sanitize_vm.sh` |
| The deployment modules accept the customer's key only — `admin_ssh_key { public_key = var.ssh_public_key }`, a required variable with no default. Nothing is hardcoded. | `modules/*/azure/main.tf` |
| ASM's image prep does the same: truncates every user's `authorized_keys`, truncates `/root/.ssh/authorized_keys`, removes `/etc/ssh/ssh_host_*`. | `hailbytes-asm/scripts/prepare_image.sh` |

**One residual to close (low risk, cheap):** `sanitize_vm.sh` explicitly
sanitises `ubuntu` and `root`. On the **Azure** builder the build user is
`packer`, so `/home/packer/.ssh` is cleaned only by `waagent -deprovision+user`
rather than by the shredding path. That is the documented, supported Azure
generalisation step and is almost certainly sufficient — but it is a different
mechanism than the one the audit trail describes. Add `packer` to the
sanitiser's user list, and add a post-sanitise assertion that no
`authorized_keys` exists under any `/home/*`. **~1 hour.**

## Claim 2 — No reverse-tunnel agent

**✅ CONFIRMED, both clouds, unambiguously.**

A search across both product repos for `ssh -R`, `autossh`, `ngrok`,
`cloudflared`, `tailscale`, `zerotier`, `teamviewer`, `frpc`, `localtunnel`,
and `reverse.?tunnel` — over `*.go`, `*.py`, `*.sh`, `*.ts`, `*.service`,
`*.hcl`, `*.json` — returns **zero matches** outside documentation prose.

Everything the image enables at boot is accounted for, and none of it is a
tunnel:

| Enabled unit | What it is |
|---|---|
| `hailbytes-sat.service` | The product. Hardened systemd unit: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `MemoryDenyWriteExecute`, `CapabilityBoundingSet=CAP_NET_BIND_SERVICE` only. |
| `hailbytes-sat-conf.service` | One-shot first-boot bootstrap (`Type=oneshot`), local only. |
| `hatchet-engine.service` | Local durable-workflow engine, gRPC on `127.0.0.1:7077`. The firewall rule is explicitly `ufw allow from 127.0.0.1 to any port 7077`. Inert on images built without the binary. |
| `postgresql` | Local database. |
| `fail2ban`, `auditd`, `chrony` | Defensive/OS hygiene. `chrony` reaches NTP servers; see claim 5. |
| `apt-daily.timer`, `apt-daily-upgrade.timer`, `unattended-upgrades` | OS patching from Ubuntu archives; see claim 5. |

UFW is `default deny incoming`, `default allow outgoing`, with 22/80/443/3333
opened.

## Claim 3 — No phone-home daemon

**⚠️ TRUE AS WRITTEN, BUT RE-STATE IT BEFORE THE NEXT CUSTOMER CALL.**

### The VM-side daemon: confirmed clean

There is no process on the VM that contacts a HailBytes endpoint. The
server-side telemetry that exists in the codebase is inert in the shipped
configuration:

| Control | Shipped value | Effect |
|---|---|---|
| `analytics.enabled` | `false` | Master switch off — nothing is even written locally. |
| `analytics.opt_out` | `true` | Second gate, also off. |
| `analytics.telemetry_url` | `""` (empty) | The forwarder goroutine is only started when this is non-empty (`analytics.Init`), so no forwarder exists. |
| `analytics.telemetry_token` | `""` | — |

Source: `hailbytes-sat/config.json` (the file Packer installs verbatim), and
`analytics/analytics.go` / `analytics/forwarder.go`. When configured, the
forwarder POSTs *anonymised* admin events (`anon_user_id`, `anon_org_id`, event
name, path) to a Cloudflare Worker — but only if an operator sets the URL
themselves. **Worth noting for a code reviewer:** the forwarder's start
condition is `cfg.TelemetryURL != ""` *independent* of `Enabled` / `OptOut`, so
the empty default is the only thing keeping it off. Gating the forwarder on
`Enabled && !OptOut` as well would make the guarantee structural rather than
configurational. **~1 hour.**

ASM is equivalent and slightly stricter: `ENABLE_ANALYTICS` defaults to
`False`, `HAILBYTES_TELEMETRY_ENABLED` defaults to `False`, and
`CLOUDFLARE_ANALYTICS_TOKEN` defaults to `''`. (The comment above that last
line claims the default "points to the HailBytes-operated aggregator" — stale
comment, the code default is empty. Worth fixing so nobody reads the comment
and believes it.) The `HAILBYTES_TELEMETRY_ENDPOINT` default
(`https://telemetry.hailbytes.com/v1/event`) is a HailBytes-controlled URL sitting
in the config, but it is unreachable-by-default because the boolean gate is off.

### The browser-side reporter: default-on, and the reason to re-state the claim

`hailbytes-sat` ships a self-hosted Sentry bundle that **loads on every admin
page and on the login page**, and initialises against a hardcoded
HailBytes-owned DSN:

```
static/js/src/sentry/sentry.js:24
  dsn: "https://25ff…@o4510488240455680.ingest.us.sentry.io/4510631328677888"
  sendDefaultPii: true
```

```
templates/base.html:17-21   templates/login.html:25-28
  window.satErrorReportingOptOut = {{if .ErrorReportingOptOut}}true{{else}}false{{end}};
  {{if not .ErrorReportingOptOut}}<script src="/js/dist/sentry.bundle.js" defer></script>{{end}}
```

`ErrorReportingOptOut` comes from `config.Analytics.ErrorReportingOptOut`, and
**the shipped `config.json` does not contain an `error_reporting_opt_out` key
at all** — so it takes Go's zero value, `false`, i.e. *not* opted out. The
script tag renders, and `sentry.js` auto-initialises on `DOMContentLoaded`.

What that means precisely:

- The traffic originates in the **operator's browser**, not on the VM. Closing
  the VM's egress does not stop it. Neither does a customer NSG on the workload
  subnet.
- The destination is a HailBytes-controlled Sentry project on **`ingest.us.sentry.io`
  — a US region.** For an EU-resident 600k-learner deal with a data-residency
  commitment, that is the material fact, more than the phone-home framing.
- `sendDefaultPii: true` is set, which enables IP collection. A `beforeSend`
  hook then deletes `event.user.email`, `.ip_address`, `.username`, filters a
  list of sensitive keys from breadcrumbs and request data, and strips
  `Authorization`/`Cookie` headers. So it is *scrubbed* — but it is
  client-side scrubbing of error payloads, which is best-effort by nature, and
  it is on by default.
- It is genuinely opt-out-able: the privacy settings page and the onboarding
  consent screen both flip `ErrorReportingOptOut`, and when set the bundle is
  not even served.

**Also relevant to an air-gap conversation:** the admin UI's CSP allows
`https://cdn.jsdelivr.net` and `https://js.sentry-cdn.com` in `script-src`
(`middleware/security.go`). The Sentry bundle itself is self-hosted, so
`js.sentry-cdn.com` is vestigial, but the Shepherd.js tutorial library **is**
lazy-loaded from jsDelivr when an operator clicks "Start Tutorial"
(`static/js/src/features/tutorial.js`). Browser-side, again, and only on that
click.

### Recommended re-statement

Replace "no phone-home daemon" with something you can defend line-by-line:

> No process on the VM contacts any HailBytes-controlled endpoint. Product
> telemetry is disabled in the shipped configuration and requires an operator
> to set a URL before anything is transmitted. Separately, the admin web UI
> loads a browser-side error reporter that sends scrubbed JavaScript exception
> reports to a HailBytes-operated Sentry project hosted in the US; it is
> enabled by default and can be turned off in Settings → Privacy, or by setting
> `analytics.error_reporting_opt_out: true` in `config.json` before first boot.

**Recommended fixes, in order of value to this deal:**

1. **Flip the default.** Add `"error_reporting_opt_out": true` to the shipped
   `config.json` so marketplace images are opt-*in* for error reporting. One
   line, and it makes the original claim true without qualification. **~1 hour
   including a template test.**
2. **Offer an EU ingest endpoint.** Sentry supports EU-region DSNs
   (`ingest.de.sentry.io`). If error reporting stays default-on for
   self-service customers, an EU DSN removes the residency objection entirely.
   **~0.5 day, mostly Sentry-side project setup.**
3. Gate the analytics forwarder on `Enabled && !OptOut` in addition to a
   non-empty URL. **~1 hour.**
4. Fix the stale ASM comment about `CLOUDFLARE_ANALYTICS_TOKEN`. **~10 minutes.**

## Claim 4 — No license-server heartbeat

**✅ CONFIRMED, both clouds.**

- No licensing code exists in either product. Searches for `license.?server`,
  `licence.?server`, `activation`, `entitlement`, `heartbeat`, `check_in`,
  `phone.?home` across `*.go`, `*.sh`, `*.service`, `*.py`, `*.ts` return only
  unrelated matches (an audit-retention worker's `checkInterval`, IMAP
  "Checking…" log lines, `dev-setup.sh` "Checking format", and prose).
- **No metering client either.** No `MeterUsage`, `RegisterUsage`,
  `marketplacemetering`, or Azure metered-billing call anywhere in the product
  code. Billing for these listings is per-vCPU, reported by the cloud platform
  from the VM's own lifecycle — the software has no part in it and cannot be
  disabled into non-compliance.
- Nothing in the deployment modules adds a licensing side-channel. The only
  AWS Marketplace API the Terraform touches is
  `marketplace-entitlement:GetEntitlements`, and that is in
  `hailbytes-static/workers/aws-to-pipedrive/lambda/enrichment.py` — a
  **HailBytes-side** CRM Lambda in our own account, reading our own
  subscription events. It never touches a customer VM.

Note for accuracy: `modules/ha-hot-hot/aws/main.tf` describes the VM egress
rule as "Egress for marketplace metering, updates, DB". Given there is no
metering client, "marketplace metering" in that comment is misleading — worth
correcting so an auditor grepping for metering doesn't chase it.

## Claim 5 — Functions with all egress closed except customer-chosen integrations

**⚠️ TRUE FOR THE PRODUCT, with three named exceptions — none of them
HailBytes-controlled.** Nothing here contacts HailBytes, and nothing here is
fatal; but the claim as phrased ("all egress closed") invites a reviewer to
close egress and diff the result, so name these first.

| Exception | What happens with egress closed | Reaching |
|---|---|---|
| **First-boot IP discovery.** `bootstrap.sh`'s `wait_for_network()` polls `canhazip.com` for up to 60 s before continuing, and `get_public_ip()` falls back to `canhazip.com`, `ifconfig.me`, `icanhazip.com`. | **Boot succeeds, ~60 s slower.** Both functions are non-fatal by design (`wait_for_network` returns 0 on timeout with a warning), and cloud IMDS is tried *first* — AWS IMDSv2 then Azure IMDS — so with metadata reachable the public-IP echo services are never called. Worst case the displayed dashboard URL falls back to `127.0.0.1` with an explicit operator warning; the admin password is **not** derived from the IP (there is a comment in the code explaining exactly why that would be an auth bypass). | Third-party IP-echo services |
| **OS patching.** `unattended-upgrades` is enabled with `APT::Periodic::Unattended-Upgrade "1"` and `Automatic-Reboot "true"` at 02:00, restricted to Ubuntu security/updates/ESM origins. | Updates silently fail; the product is unaffected. **Flag this separately to the customer:** it means the image *does* self-patch the OS by default and *will* reboot itself, which sits oddly beside the "patches are customer-initiated" line in `PATCHING_AND_MIGRATION.md`. That claim is about the HailBytes application image, not the OS package set — but say so explicitly rather than letting a reviewer find the contradiction. | Ubuntu archives |
| **Time sync.** `chrony` is enabled by hardening. | Clock drifts. On a long-lived VM this eventually breaks TOTP/MFA and certificate validation. Point customers at their cloud's internal NTP (`169.254.169.123` on AWS; the Azure host clock) rather than leaving it broken. | NTP servers |

Additionally, **browser-side** (not VM egress, and so not covered by the claim
either way, but reviewers conflate them): the Sentry reporter under claim 3, and
the jsDelivr-hosted Shepherd.js tutorial, which fails with an error toast if
blocked.

Everything else genuinely works closed: the database is local or in-VNet, the
encryption key and admin password are generated on-box with `openssl rand`,
TLS certs are self-signed on-box, migrations run against the local/managed
Postgres, and every integration (SMTP, IMAP, webhooks, SIEM, Slack, threat-intel
providers, cloud connectors) is operator-configured and inert until configured.

## Has any of this become false since May?

**I cannot answer that from these clones, and I want to be explicit rather
than reassuring.**

All four repos are **shallow clones**. `hailbytes-sat` has 173 commits with the
oldest dated **2026-05-21**. `git log --diff-filter=A` attributes both
`static/js/src/sentry/sentry.js` and `analytics/forwarder.go` to the merge at
the shallow boundary (`162158e`, 2026-05-21) — which is an artifact of the
truncated history, not evidence that they were added then. They may well
predate it.

So: **the current state is as described above.** Whether the Sentry reporter
existed when you made the claim in writing needs a full-history check:

```bash
git clone --filter=blob:none https://github.com/HailBytes/hailbytes-sat
git log --follow --diff-filter=A -- static/js/src/sentry/sentry.js
git log --follow -p -- config.json | grep -n 'error_reporting_opt_out'
```

If it postdates the claim, that is a disclosure conversation, and the
one-line default flip above closes it cleanly. If it predates the claim, the
claim was imprecise when made and the re-statement above is the fix. Either
way the remedy is the same and it is cheap; the difference is only in how you
raise it.

What did land in the audited window (2026-05-01 → 2026-07-26) and touches this
audit: `28596cc` purged telnet/inetutils from the image (CVE-2026-32746),
`5915aa6` fixed silently-masked failures in boot/CI scripts, `555e8bd` fixed
encryption-key drift and HA secret wiring, `eef1c7c` lowered SSH
`ClientAliveInterval` for Azure certification. All four move in the right
direction; none of them adds an access path.
